# Smart Attendance & Field Activity Monitoring System

AI-enabled attendance and field-activity monitoring for rural development field workers (Chengalpattu District, Tamil Nadu). It's a Flutter Android app running on **Firebase Authentication** and **Cloud Firestore**, so there's no separate backend server to deploy.

> ⚠️ **Build status: not yet compiled or device-tested.** See [`docs/STATUS.md`](docs/STATUS.md) for exactly what is verified and what isn't.
>
> **Start here:** [`docs/GITHUB_UPLOAD_AND_BUILD.md`](docs/GITHUB_UPLOAD_AND_BUILD.md) is a step-by-step beginner guide to uploading to GitHub, adding secrets and downloading the APK. Signing key care: [`docs/SIGNING_KEY.md`](docs/SIGNING_KEY.md).

> **Synthetic data notice.** No official worker records, employee IDs or GIS boundaries were available during development. Every demo record is generated by the app and labelled **SYNTHETIC DEMO** in the UI (Product Report §5.4 and §9). Official data can be loaded through *Workers → Add/Edit* and *GIS boundaries → Import GeoJSON*.

## Technology stack

| Layer | Choice | Why |
|---|---|---|
| Frontend | Flutter 3.27 (Dart 3.6), Material 3 | Mandatory; one modular codebase |
| Authentication | Firebase Auth: Google Sign-In, email/password, registration, password reset | Mandatory; secure credential handling and hashing done by Google |
| Database / backend | Cloud Firestore and Firestore Security Rules | Serverless and real-time: the dashboard updates live across phones, works offline and syncs later, free Spark plan, no hosting |
| Authorisation | Role field in `users/{uid}`, enforced server-side by `firestore.rules` | Role-based access that can't be bypassed from the client |
| Maps / GIS | OpenStreetMap tiles via `flutter_map`, on-device point-in-polygon | No API key; real tiles, real geometry |
| GPS | `geolocator` (accuracy, timestamp, mock-location detection) | |
| AI face verification | Google ML Kit face detection plus a MobileFaceNet TFLite embedding model, compared by cosine similarity | Runs on-device and offline; nothing is sent to third parties |
| Charts | `fl_chart` | |
| CI/CD | GitHub Actions: tests, then a signed release APK, then a GitHub Release | |

```
Flutter Android app  ──(Firebase SDK, TLS)──►  Firebase Auth
        │                                          │ ID token
        └──────────────────────────────────►  Cloud Firestore  (security rules = API authorisation layer)
On-device services: ML Kit + TFLite (face), Geolocator (GPS), GIS geometry engine, alert rule engine
```

## Modules (Product Report §5)

| § | Module | Where in the app |
|---|---|---|
| 5.1 | Auth & user management | Login, Register, Forgot password, Google Sign-In, Logout, role-based navigation, account status (active/inactive/suspended) |
| 5.2 | Worker management | Workers tab: search, filter, create, edit, employee ID (human-facing) vs database ID, supervisor and boundary assignment |
| 5.3 | AI face verification | Face enrolment (2 samples, consent, consistency check) and verification at check-in. Returns `worker_id, verified, similarity, status, message, timestamp`. Shows *unavailable / not enrolled / no face* states and never reports a false success |
| 5.4 | GPS & GIS | Live GPS with accuracy and mock detection, point-in-polygon, distance to edge, an uncertainty flag when the accuracy circle crosses the edge, boundary attributes (`boundary_id, layer, attribute_column, attribute_value`), live tracking while on duty, draw/import boundaries |
| 5.5 | Attendance | Check-in/out with linked face and location results. Statuses: present, late, pending verification, rejected, absent. History, plus supervisor review/override with a mandatory note |
| 5.6 | Tasks & activities | Create/assign tasks; assigned, in-progress, submitted, completed and overdue states; activity submission with GPS stamp and up to 3 compressed photos; supervisor approve/reject |
| 5.7 | Alerts | Face failed, outside boundary, mock GPS, late check-in, attendance missing, task overdue, low GPS accuracy. Each has severity and status, can be resolved with remarks, appears as a live in-app banner, and each rule can be switched on/off |
| 5.8 | Dashboard & analytics | Live KPIs, attendance pie, 7-day trend, verification outcome bars, task chart, live map, recent alerts, date/block/panchayat filters. Reports: date range, worker and location filters, CSV export |
| 11 | Security & audit | Server-side rules, consent capture, biometric reference deletion, append-only `audit_logs` |

## Roles

The **first account to sign in becomes Administrator** automatically. Later accounts start as **Field Worker**, and an admin promotes them under *Workers → Edit → Role*.

| Role | Navigation |
|---|---|
| Field Worker | Home (check-in/out, area map), Tasks, History, Alerts, Profile |
| Supervisor | Dashboard, Live Map, Workers, Tasks, More (attendance register, activity review, alerts, boundaries, reports, audit) |
| Administrator | Same as Supervisor, plus role management, Settings & rules, demo data |
| Auditor / Analyst | Dashboard, Map, Reports, Audit (read-only) |

## One-time Firebase setup

1. Firebase project `smart-attendance-dda5f`, Android app `in.cit.smartattendance`, with the release SHA-1/SHA-256 added. ✅ done
2. Authentication → Sign-in method: **Email/Password** and **Google** enabled. ✅ done
3. Firestore Database created (production mode).
4. **Publish the security rules:** open Firebase console → Firestore Database → **Rules**, replace everything with the contents of [`firestore.rules`](firestore.rules), then click **Publish**. Without this step, production mode denies every read and write.

## GitHub secrets (release signing)

Google Sign-In only works when the APK is signed with the key whose SHA-1 is registered in Firebase. The workflow reads that key from repository secrets (*Settings → Secrets and variables → Actions*):

| Secret | Value |
|---|---|
| `KEYSTORE_BASE64` | base64 of `smartattend-release.jks` |
| `KEYSTORE_PASSWORD` | keystore password |
| `KEY_ALIAS` | `smartattend` |
| `KEY_PASSWORD` | key password |

The workflow refuses to build if the keystore SHA-1 doesn't match `31:E3:3E:99:…:0F:AC`. It also verifies the final APK signature.

## Building

**CI:** every push to `main` runs analysis, unit tests and a release build, then publishes the APK under **Releases** (and as a workflow artifact).

**Locally:**
```bash
flutter pub get
curl -L -o assets/models/mobilefacenet.tflite https://github.com/MCarlomagno/FaceRecognitionAuth/raw/master/assets/mobilefacenet.tflite
# put key.properties + release.jks in android/ (see workflow for format)
flutter build apk --release
```

## Demo script

1. Install the APK and sign in with Google. As the first user, you become Admin.
2. Go to *More → Settings & rules → Load synthetic demo data*. Demo zones are created **around your current location**, so GIS validation works where you are.
3. Explore the Dashboard, Live Map (workers inside/outside zones), Workers, Tasks and Reports.
4. Make yourself a worker for the field demo: *Workers → (you) → Edit*. Assign *Demo Zone A* and set an employee ID. Then on a second phone or account, register as a worker and check in to show face and GIS verification. (Alternatively, an admin can assign a second Google account as worker.)
5. Walk outside the zone while checked in. An **outside-boundary** alert appears live on the admin phone.
